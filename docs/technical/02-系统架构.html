一总体分层

1.1四层结构与依赖方向

整个应用是一个由 Vite 6 构建的 React 18 单页应用，全程运行在 TypeScript 5.7 严格模式之下。自上而下分为四层：界面层、状态层、核心服务层与运行时层，依赖方向严格自上而下，低层从不反向导入高层。这一约束使每一层都可以独立理解、独立测试——统计内核不需要知道界面的存在，插件运行时也不关心某个按钮画在哪里。

图 1　四层结构：依赖方向自上而下，低层从不反向导入高层

1.2各层职责与技术选型

层职责主要技术
界面层路由、工作台四区布局、三种模式编辑器、对话框与新手引导React 18、react-router-dom 7

二启动时序

应用启动遵循"先自检、再加载、后恢复"的固定顺序。欢迎页先完成硬件自检，进入工作台后按序加载核心插件并恢复上次会话，任何一步的环境缺失都会如实报告而不是静默降级。

图 2　启动时序：自检、加载、恢复三步固定顺序

欢迎页的自检结果同时决定后续行为的"档位"：WebGPU 可用则计算走 GPU 加速；WASM 模块存在则走 Rust 参考引擎；两者皆缺时，插件以 CPU 完成同样的数学。这个决定在启动时一次性做出并显示在状态栏，用户随时知道"现在是谁在算"。

自检报告采取"如实告知"原则：缺什么就提示什么，给出建议（例如换用支持 WebGPU 的浏览器），但绝不假装能力存在。这是产品在环境适配上的基本立场。

三状态管理

3.1六个状态库的职责划分

六个 Zustand 状态库承载全部应用状态。跨界的 UI 通信走一个小型类型化事件总线（src/core/events.ts），例如插件参数变化、宿主文件选择对话框等事件。状态库之间通过事件总线协作而非直接引用，避免环状依赖。

状态库职责
appStore宿主状态、横幅与通知、性能指标、面板开关
projectStore当前项目、最近列表、保存与自动保存、分享、参数持久化
pluginStore插件注册表、加载与激活生命周期、文件分发、宿主容器、内置插件加载失败重试
settingsStoreGPU 模式、自动保存间隔、语言等偏好，语言以 i18n 模块为唯一权威源并双向订阅
blockStore流程模式图状态、运行编排、节点输出缓存、运行取消
editorStore积木与代码模式的会话（IR、代码文本、变量、控制台），载入时逐字段净化

3.2项目生命周期与持久化

项目生命周期覆盖创建、打开、保存、自动保存与分享五个动作。项目格式为 .clproj，内容经 lz-string 压缩后存入浏览器 IndexedDB；整个流程模式图、积木程序与代码会话都持久化进项目文件，重新打开时完整恢复，不存在"换一个模式就丢进度"的问题。

分享链接由随机 UUID 标识，载荷在解析端做大小与结构双重校验，拒绝畸形数据——分享是产品里少有的"数据离开本机"的路径，因此对载荷的防御做得格外保守：超出尺寸上限直接拒绝，结构不符逐字段丢弃，绝不会把不可信的内容直接灌进编辑器。

自动保存间隔可由用户在设置中调整，保存动作落在 projectStore 一个库里，流程图、积木程序与代码会话对存储层完全透明——三个编辑器只需要把自己的会话状态交给项目状态库即可。

四渲染管线

中央视口拥有三个绘图表面，宿主集中管理其可见性：

  1. 共享 2D canvas：所有 2D 插件（散点、折线、直方图、热力图、等值线、箱线、小提琴、桑基等 30 余个）画在同一个画布上，由统一的 2D 视口抽象（viewport2d）提供快照式访问，插件卸载不会撕裂画布。
  2. DOM 容器：供需要 DOM 元素的插件使用，也是沙箱插件经 OffscreenCanvas 转移后挂载画布的位置。
  3. 宿主管理的 Three.js 3D 场景：只有声明了 renderToScene 能力的插件激活时才按需创建，并配套轨道控制、灯光网格与尺寸自适应。

六依赖规则与分包策略

  • 依赖方向单向：界面层依赖状态层，状态层依赖核心服务层，核心服务层绝不导入界面层。
  • 核心服务保持"少 DOM"：纯函数服务（i18n、文件格式、统计、绘图、存储适配器）全部可在 Node 环境单元测试。
  • 契约收口：插件契约（src/types/plugin.ts）是宿主与第三方代码之间唯一的共享词汇表；渲染桥接（src/blocks/render.ts）是区块系统唯一带副作用的模块，负责把可视化输出送进插件渲染器，使编译器与执行器保持可测。
  • 重依赖全部懒加载分包：Blockly（约 828 KB）在首次进入积木模式时才拉取，TensorFlow.js 在首次点击训练时才拉取，Pyodide 运行时在首次运行 Python 时才引导；标准与流程模式的首屏不受影响。
  • 错误隔离：错误边界按区域隔离（顶栏、状态栏独立包裹），边界重置通过递增 key 实现有界重试，避免错误死循环。
懒加载的分包边界与依赖规则是同一枚硬币的两面：正因为重依赖只被少数模式引用，才可能把它们安全地推迟到首次使用时再下载；反过来，若某层偷偷反向依赖了重依赖，分包优化会立即失效。构建产物体积因此在持续集成中被间接守护。

七可观测性

  • 性能监控（perf）：帧时间与 GPU 时间聚合，超阈值时经通知系统提示用户而非静默卡顿。
  • 运行日志（logger 加 download）：会话事件序列可导出为文件，用于问题反馈与回归定位。
  • 状态栏：常驻显示 GPU 可用性、当前引擎与性能指标，用户随时知道"现在是谁在算"。

三条可观测性通道共同构成一个原则：应用内部发生了什么，用户与开发者都应当能看到。性能问题以通知浮出，运行历史可以带走，当前引擎常驻可见——静默失败与静默降级在架构层面就被排除。
